# Foreman 实验笔记：6 局 A/B（2026-09-05/06）

本文是 README 实测数据的方法论与完整账目。目的：回答三个问题——**Q1** 工头模式省不省云端 token；**Q2** 质量是否守得住；**Q3** 架构边界在哪（工人只能"当手"，还是能"当脑"）。

## 方法

2×2 设计：两个任务 × {标准预设, Foreman 预设}，同一提示词（仅运行目录路径一个字符之差），每次运行一个全新隔离沙箱（模板逐字节拷贝），验收为客观复验清单（测试通过数 + 规格期望值逐格核对）。主模型经用户两次调整：task1 对使用 glm-5.2，task2 对使用 deepseek-v4-flash——因此**只在配对内比较 token，跨模型只比行为**。

- **task1（偏"手"）**：logkit 日志巡检 CLI——规格完全钉死（129 行混合格式样本、错误计数预先锁定），四个子命令 + ≥12 测试 + README，交付量约 700 行。
- **task2（偏"脑"）**：看板 CLI v0.2 改造——需求书只钉 CLI 外部行为，三个模块（优先级到期 / 导入导出 / 通知摘要）内部设计留白，考验简报质量与验收-补丁循环。

## 结论

1. **Q1（省钱）**：四轮无一例净省。但归因清晰——R2 的 2.63× 中 42% 是稳定性税（废运行 + 重启），干净主体仍 +54%，元凶是 glm-5.2 单步 2 万 token 的推理膨胀；R4 反而比标准臂省 33%，但那是单轮无死亡 + 纪律自身开销极小的功劳，不是委托的功劳。**成本由三个一阶因子决定：稳定性税 > 编排者思考风格 > 简报开销比。**
2. **Q2（保质）**：四轮交付全部绿灯（21/24/38/38），纪律不伤质量。
3. **Q3（边界）**：**两个任务被纪律路由到相反且各自正确的模式**。task1（规格钉死、输出密集）委托成功；task2（判断密集）被红线正确弹回单干，拒绝理由与经济学一致（"把设计写进简报的开销约等于实现本身"）。边界判据 = 简报开销比，且决策外显规则使这个判断可审计。
4. **输入侧是未开发的大头**：billable 的 64–78% 是输入 token，执行委托完全不触碰它——这就是 v2 加入只读侦察车道（scout_worker）的动机。

## 过程事故记录（都有产品产出）

- **R2 v1 作废**：编排者加载技能、验算规格一切正常，但"决定是否委托"的关键步骤遭遇 API 五连重试死亡；用户"继续"后模型直接以自己实现身份落盘。全程 0 次委托调用，而工具在目录里、技能内容在上下文里。定性：纪律是提示词级的，turn 中断后决策无声蒸发。
- **处置**：加"决策外显"硬门槛（写入任何实现文件前必须已委托或写明不委托理由）。R2 v2 中规则生效：先外显 todo 计划，首次委托发生在任何写入之前；task2 的 R4 中规则再次生效，产出了一次教科书级的有据拒绝。

## 复现须知

- 样本量为 1 对 × 2 任务，单次运行不做定论；验收分差 ≤1 视为噪声。
- Foreman 臂的简报与报告回传计入其云端开销（架构的真实成本，不剔除）。
- 对照组（标准预设）自带云端 `subagent` 工具，主模型未自发使用，无混杂。
- 工人档位、思考强度、限流策略的变化会改变绝对数字；三个一阶因子的相对排序在两对中保持一致。

## v2：真实项目对照（2026-09-06，psc）

v1 的两个任务都是合成任务。v2 把考场搬到真实项目：一个 FastAPI + SQLAlchemy + JWT 的商品采集云服务（30 文件，脱敏称 psc），逐字节拷贝两份作为隔离沙箱，原项目零接触，两臂共享同一套已装依赖。

- **任务**：用户级"搜索历史"——分页查询 + 删除自己的记录 + 前端入口 + `DATABASE_URL` 环境变量覆盖（可测试性改造）+ pytest/TestClient 测试。刻意设计为高广度低触深：需读约 15 个文件（应用主文件 600+ 行），实际改动 3~5 个。
- **P-STD（标准预设，glm-5.2）**：in 152,125 / out 58,481 / billable 210,606；1 轮，0 死亡。
- **P-FM（工头预设，glm-5.2）**：in 130,751 / out 32,002 / billable 162,753；1 轮，3 次重试。
- **行为（本局最重要产出）**：P-FM 工具表含 scout_worker（`list_subagent_models` 单例修复的生产验证），但**两次外显拒绝**——勘察决策「自读，理由：库小一次能读完，且改动文件占要读大半，侦察无转述价值」；委托决策「不委托，自己干：细节取舍密集（限流中间件规避、TestClient 时序、created_at 格式、DATABASE_URL 守卫）」。两次拒绝均符合技能判据，纪律开销 ≈ 0。
- **质量**：两臂在全部行为探针上等价（pytest 各 5 绿、`scraper.db` 逐字节未动、401/分页结构/倒序/越权 404/删除 200/`DATABASE_URL` 覆盖/回归全过），无越界文件改动（std 多改一个 .gitignore，轻微超范围）。

### v2 结论

1. **−22.7% 的 billable 差不能归因给 Foreman 功能**（两功能调用次数均为 0）——可归因部分是实现策略差异：std 整文件重写 ×10（out 58K），fm 单写 + 9 次编辑（out 32K）。
2. **glm-5.2 同预设同任务的运行间波动 ≈ 29%**：单对样本的噪声远大于小差异——在 glm 上做小差异 A/B 是噪声里捞针；对比实验要么多对采样，要么换稳定模型。
3. **决策外显累计 6 次全部正确**（2 次委托 + 4 次拒绝），含一次对侦察车道的有据否决（"改动占读取大半"压过"文件数阈值"）。
4. **任务规模教训**：27 文件/4 目录技术上触发侦察阈值，但第二判据正确否决。替读经济学只存在于"读远大于改"的仓库——输入侧验证需要真正的大仓库。
5. **方法学教训**：会话头部 `agentPreset` 字段记录宿主默认预设，不可作为预设归属判据；权威判据 = `agent-preset/selected` 事件 + 系统提示文本 + 工具目录三件套。

### 量化的边界（写给使用者）

在 glm-5.2/deepseek 这类便宜脑上，Foreman 的两项功能在中小项目日常开发中**大部分时间会正确地不点火**——这是纪律在按经济学工作，不是故障。它产生净收益的条件：贵脑（opus 级，产出贵 30–100 倍）、输出密集且规格可引用的任务、或"读远大于改"的大仓库。批量任务（整包迁移/批量测试生成）适合 Runner 形态而非会话纪律。
