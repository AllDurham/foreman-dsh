# Foreman 实验笔记：4 局 A/B（2026-09-05/06）

本文是 README 实测数据的方法论与完整账目。目的：回答三个问题——**Q1** 工头模式省不省云端 token；**Q2** 质量是否守得住；**Q3** 架构边界在哪（工人只能"当手"，还是能"当脑"）。

## 方法

2×2 设计：两个任务 × {标准预设, Foreman 预设}，同一提示词（仅运行目录路径一个字符之差），每次运行一个全新隔离沙箱（模板逐字节拷贝），验收为客观复验清单（测试通过数 + 规格期望值逐格核对）。主模型经用户两次调整：task1 对使用 glm-5.2，task2 对使用 deepseek-v4-flash——因此**只在配对内比较 token，跨模型只比行为**。

- **task1（偏"手"）**：logkit 日志巡检 CLI——规格完全钉死（129 行混合格式样本、错误计数预先锁定），四个子命令 + ≥12 测试 + README，交付量约 700 行。
- **task2（偏"脑"）**：看板 CLI v0.2 改造——需求书只钉 CLI 外部行为，三个模块（优先级到期 / 导入导出 / 通知摘要）内部设计留白，考验简报质量与验收-补丁循环。

## 结论

1. **Q1（省钱）**：四轮无一例净省。但归因清晰——R2 的 2.63× 中 42% 是稳定性税（废运行 + 重启），干净主体仍 +54%，元凶是 glm-5.2 单步 2 万 token 的推理膨胀；R4 反而比标准臂省 33%，但那是单轮无死亡 + 纪律自身开销极小的功劳，不是委托的功劳。**成本由三个一阶因子决定：稳定性税 > 编排者思考风格 > 简报开销比。**
2. **Q2（保质）**：四轮交付全部绿灯（21/24/38/38），纪律不伤质量。
3. **Q3（边界）**：**两个任务被纪律路由到相反且各自正确的模式**。task1（规格钉死、输出密集）委托成功；task2（判断密集）被红线正确弹回单干，拒绝理由与经济学一致（"把设计写进简报的开销约等于实现本身"）。边界判据 = 简报开销比，且决策外显规则使这个判断可审计。
4. **输入侧是未开发的大头**：billable 的 64–78% 是输入 token，执行委托完全不触碰它——这就是 v2 加入只读侦察车道（scout_worker）的动机。

## 过程事故记录（都有产品产出）

- **R2 v1 作废**：编排者加载技能、验算规格一切正常，但"决定是否委托"的关键步骤遭遇 API 五连重试死亡；用户"继续"后模型直接以自己实现身份落盘。全程 0 次委托调用，而工具在目录里、技能内容在上下文里。定性：纪律是提示词级的，turn 中断后决策无声蒸发。
- **处置**：加"决策外显"硬门槛（写入任何实现文件前必须已委托或写明不委托理由）。R2 v2 中规则生效：先外显 todo 计划，首次委托发生在任何写入之前；task2 的 R4 中规则再次生效，产出了一次教科书级的有据拒绝。

## 复现须知

- 样本量为 1 对 × 2 任务，单次运行不做定论；验收分差 ≤1 视为噪声。
- Foreman 臂的简报与报告回传计入其云端开销（架构的真实成本，不剔除）。
- 对照组（标准预设）自带云端 `subagent` 工具，主模型未自发使用，无混杂。
- 工人档位、思考强度、限流策略的变化会改变绝对数字；三个一阶因子的相对排序在两对中保持一致。
